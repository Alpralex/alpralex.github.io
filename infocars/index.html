Overview

The problem and what I built

The problem

Dealers price used cars by gut feel and by browsing a few listing sites. The data exists, but it is scattered across portals, duplicated, and written inconsistently. The same car can appear as "Onix 1.0 LT", "ONIX LT 1.0 FLEX" or with a typo in the version.

What I built

An end-to-end pipeline that collects listings every day, normalises them into one clean model of make, model, version and year, and serves the result through dashboards and an AI assistant. I designed and built it, from scraping to the product a customer sees, and it was sold to a Brazilian car dealer.

How it works

Four steps from a messy ad to a price

1 · Match each ad to a catalogue

Sellers write the same car in many ways: "Onix 1.0 LT", "GM ONIX LT 22/23", "onix lt flex". The matcher cleans the text, matches aliases on whole words so "LT" never matches "LTZ", reads the model year from "22/23", and falls back to fuzzy matching for typos such as "Corola". In production this cut 5,114 model spellings to 641 real models and corrected 26,071 ads.

2 · Drop bad prices

Ads go out when the price is missing, out of range, or far from comparable cars. The most common error is a price typed without its last digit, which still looks like a plausible car price, so a fixed range does not catch it and a comparison with similar cars does.

3 · Build market statistics

For each version, year and state: median asking price, 25th and 75th percentiles, and median days on the site. An ad that disappears is treated as sold on its last day online. In production these were materialised views in PostgreSQL.

4 · Answer the dealer

Dashboards show what similar cars sell for, where a car sits against the market and which stock is priced out of line. The assistant answers the same questions in plain language.

Result

Comparing the dealer's own figures before and after adoption, the saving was about R$2,000 (roughly €300) per vehicle negotiation, and time in stock came down to one to three months.

AI layer

Three designs for the pricing assistant

The final model was chosen by running the same test questions against each design.

v1

Function calling

OpenAI and Grok models call predefined functions to fetch data. A test suite compares the models' answers on the same questions.

v2

SQL agent

The model writes SQL against the modelled tables, reading only from an approved list of tables.

v3 · final

Claude tool use

Anthropic Claude API with tool use. Prompt caching on the system prompt and tool definitions keeps cost and latency down.

Tools

Three tools: market_price, price_position and a guarded run_sql. The system prompt and tool definitions are cached, because they are identical on every call.

Guardrails

SQL written by the model is checked before it runs: one SELECT only, approved tables only, no comments, and a row limit added. In production it also ran under a read-only database role.

Try it

Run the demo in a minute

The repository is a rebuilt sample written for this portfolio. It shows how the main parts worked on 1,200 synthetic listings, and does not contain the production code, real listings or the scraper. The demo uses SQLite, so it runs without a database server; the PostgreSQL schema, market views, quality checks and read-only role are in sql/postgres/.

git clone https://github.com/Alpralex/infocars-pricing-showcase
cd infocars-pricing-showcase
pip install -r requirements.txt
python scripts/demo.py     # quality report, market price, price position
pytest                     # 33 tests
